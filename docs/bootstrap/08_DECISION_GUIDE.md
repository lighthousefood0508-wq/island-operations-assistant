# Decision Guide

Future Decision records should be written in a consistent format so Codex, GPT, Claude, Gemini, and human reviewers can interpret scope the same way.

## Purpose

State why the decision exists.

Example:

```text
Purpose:
Clarify whether category codes are user-entered or system-generated.
```

## Problem

Describe the operational or technical problem.

Include current behavior, observed issue, and why it matters.

## Alternatives

List realistic options.

Each alternative should include:

- What changes
- What stays the same
- Risk
- Operational impact
- Architecture impact

## Decision

State the chosen option directly.

Use precise language:

```text
Decision:
categoryId remains the official foreign key.
categoryCode is generated by the system.
displayName remains editable by the operator.
```

## Scope

Define what is allowed.

Examples:

- Files or modules allowed
- UI only
- API allowed or not allowed
- Migration allowed or not allowed
- Tests required

## Deferred

List what is intentionally not included.

Deferred items must not be implemented by assumption.

## Verification

Define how completion will be proven.

Examples:

- Unit tests
- Integration tests
- E2E tests
- Architecture guards
- Manual device checks
- Screenshots
- `verify:full`

## Compatibility

Every implementation Decision should include a compatibility check:

```text
Reviewed ADR:
- ADR-013
- ADR-014
- ADR-015

Compatibility Result:
- No Product Contract change
- No schema change
- No domain boundary change
```

If compatibility is unclear, stop before implementation.

## Future Impact

Explain what this decision enables or prevents later.

Good future-impact notes include:

- Migration consequences
- Operator workflow impact
- Whether a later phase can extend it
- Whether it closes or opens a domain boundary
- Whether it creates a new source of truth
