## 3. Completed Product Capabilities

- Central SQLite is the only formal source of live business data.
- Catalog owns categories, products, drafts, immutable published versions, channel settings, and Product Contract v2.
- New category codes are generated by the backend as `cat-0001` style identifiers. Existing legacy category codes are preserved.
- Operations owns Events, Event product snapshots, sellable inventory, Orders, lifecycle records, closeout data, and operational audit.
- Event codes are generated safely by the backend as `YYYYMMDD-01`, `YYYYMMDD-02`, and so on.
- A single operational Event may exist at a time.
- Event lifecycle now supports `draft`, `open`, `paused`, `closed`, and `archived`.
- Back Office can pause an OPEN Event, atomically adjust the full Event inventory page, and resume service.
- Draft and Paused Events can add formally published Catalog product versions to the Event.
- Batch inventory saves are transaction-safe, idempotent, audited, and preserve sold/reserved lower bounds.
- `customerAvailableQuantity` is centrally derived from current remaining quantity minus the safety buffer.
- A product can be disabled for the current Event without changing Catalog.
- POS cannot create Orders while the Event is paused.
- Kitchen can still read and finish existing Orders while the Event is paused.
- Formal Event Close remains the single `LifecycleService.closeEvent()` path.
- Closing requires an explicit per-product closeout record: remaining quantity is divided into waste and retained quantity.
- Unresolved Orders still block close. Close remains idempotent and produces the daily report snapshot.
- POS Order creation retains atomic inventory consumption, Event-local order numbers, idempotency, immutable item snapshots, and audit.
- Order, Payment, and Production states remain independent under ADR-014.
- Back Office is Event-first. Catalog remains a separate low-frequency product-master page.
- Statistics displays zero rather than `null` and provides the closeout/waste confirmation workflow.
- SSE remains notification-only. POS, Kitchen, and Statistics re-fetch central state through REST.

## 6. Domain Boundaries

- Catalog owns categories, product data, selling price, description, channels, drafts, and published versions.
- Canonical Ingredient Identity Authority owns `ing_<uuid>` and Ingredient Measurement Profile identity, binding, lifecycle, immutable versions, Active uniqueness, and history.
- Measurement Foundation owns dimensions, stable unit identity, exact conversions, locale policy, canonical normalization and evidence, precision/no-rounding, and Profile validation semantics.
- Canonical Ingredient and Measurement capabilities are currently hosted in Recipe Core; hosting does not make them Recipe-owned.
- Recipe owns Recipe ingredient intent, quantities, presentation, immutable Published Recipe Versions, Standard Yield, and canonical projection/scaling requests. Existing Recipe `measurementDimension` is compatibility-only.
- Operations owns Events, Event inventory, remaining quantity, reservations, safety buffer, Orders, closeout observations, and operational audit.
- Kitchen changes Production state only.
- Cost owns purchase quotes, package pricing, accepted purchase and normalized costing evidence received through approved contracts, valuation, cost calculation, allocation evidence, and Cost Snapshots. Operations closeout waste does not pretend to be Cost data.
- Payment owns future provider integration and reconciliation. Current POS payment-method capture does not constitute a completed Payment domain.
- Customer/Kiosk/Preorder remain deferred unless a later Decision approves them.
- Product Contract v2 remains the Catalog-to-Operations published-product boundary.
- Measurement and Ingredient Profile contracts are the only Measurement authority available to Recipe and Cost.

`tw_catty` always equals exactly `600 g` and cannot be overridden by Profile or Supplier. Package identities such as `包`, `袋`, `盒`, and `罐` are deferred Package Specification concepts, not Measurement Units.

Do not create a second API, second inventory source, second close path, or direct cross-domain repository access.

## 7. Important Operating Rules

- Event is the highest Back Office operating context.
- The operator flow is Event → products → inventory → open → POS → Kitchen → pause/adjust if needed → resume → closeout → close → statistics.
- Inventory is editable only while the Event is Draft or Paused.
- OPEN inventory is locked. Pause first, save the whole page once, then resume.
- Batch adjustment retries with the same idempotency key and payload return the original result.
- A changed payload cannot reuse an existing idempotency key.
- Planned quantity cannot be reduced below sold plus reserved quantity.
- Event-local disablement removes a product from active POS availability without mutating the Catalog product.
- POS cannot bypass Event status or inventory rules.
- Kitchen cannot modify Order state, Payment state, price, product, quantity, inventory, or Event state.
- Closing never automatically completes or cancels Orders.
- Closing requires explicit closeout confirmation for every Event product.
- Waste and retained quantity must add up to the recorded remaining quantity.
